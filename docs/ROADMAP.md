# Единый план AQYL — «Аким на 5 часов»

Документ сводит **командный план (этапы 1–9)**, текущее состояние репозитория и требования Strong-демо из [DEVELOPER_HANDOFF.md](DEVELOPER_HANDOFF.md). Цель: 3–5-минутное демо с проверяемым Score, одной рассчитанной альтернативой и аккуратным AI/evidence. Формула и датасет **не меняются**.

**Цепочка демо:** CALCULATE → UNDERSTAND → CHALLENGE → LEARN → DECIDE

## Этапы 1–5 — сделано (кратко)

### 1. Инфраструктура
Одна команда: `docker compose up --build`. Frontend ходит на backend только через same-origin proxies. Ветка работы — `main`.

### 2. Данные и движок
Официальные правила: 5 районов, 10 показателей, 14 мер, бюджет 100, лаги, синергии, несовместимости. Контроль: база **52,55768**, пример **56,54307**. Тесты в `backend/tests/`.

### 3. API
| Маршрут | Роль |
| --- | --- |
| `GET /api/v1/catalog` | город, baseline, default_scenario |
| `POST /api/v1/preview` | 0…5 решений, всегда 200 при валидном JSON |
| `POST /api/v1/simulate` | ровно 5 допустимых; иначе 422 |
| `POST /api/v1/council/stream` | NDJSON: simulation → mode → review/reply → done/error |

Отдельного `/validate` нет: проверка внутри preview/simulate.

### 4–5. UI
Экраны City / Decisions / Result, счётчик `N/5`, бюджет, локальный + remote preview, Leaflet-схема районов (сверх брифа; не GIS). Пользователь проходит сценарий и видит Score из движка.

**Дожать в рамках UI (не отдельный этап):** панель «Почему изменился Score?» (`breakdown_*`, `applied_interventions`, лаги, синергии), proof-строка `5/5 · 95/100 · …`, прокси `api/council/stream`.

## Оставшиеся этапы — где и как

Порядок обязателен: **6 → 7 → 8**, затем при времени **9**. Не начинать P2/этап 9 до закрытия Strong-пути.

### Этап 6 — AI-совет экспертов

**Зачем:** объяснить рассчитанный сценарий тремя ролями; Score остаётся от движка.

**Где:**
| Слой | Файлы |
| --- | --- |
| Backend (есть) | `backend/app/council.py`, `POST /api/v1/council/stream` |
| Frontend proxy | `frontend/src/app/api/council/stream/route.ts` (создать) |
| Frontend UI | блок на `ResultScreen` + состояние в `SimulatorProvider` |
| Контракты | события NDJSON в `contracts.ts` |

**Как:**
1. Проксировать stream без произвольного upstream URL (как simulate).
2. На экране результата кнопка «Слушать совет» / автозапуск после simulate — по продуктовому решению; ошибка AI **не** прячет Score.
3. Рендерить события по мере прихода: `simulation` (уже есть) → `mode` → 3× `review` → 3× `reply` → `done` | `error`.
4. Адаптировать тексты ролей под 10 показателей (уже частично в `MISSIONS`): урбанист T/E/среда; финдиректор cost/эффективность; житель слабые районы и critical &lt; 40.
5. Явно помечать `demo` vs `openai`. Без ключа — программные реплики, не «настоящий» совет.

**Приёмка:** контрольный сценарий → совет появляется потоком; обрыв AI оставляет Score и «Почему?» видимыми.

**Оценка:** 3–5 ч.

### Этап 7 — Инструмент допустимых замен + связка с советом

Это ядро Strong из handoff: **«Оспорить мой план»** = проверяемый поиск одной замены (не глобальный оптимум).

**Где:**
| Слой | Файлы |
| --- | --- |
| Backend | `backend/app/challenge.py` (новый), схемы в `schemas.py`, маршрут в `main.py` |
| Тесты | `backend/tests/test_challenge.py` |
| Frontend | `api/challenge/route.ts`, сравнительный блок в `ResultScreen` |
| AI (опционально поверх) | короткий разбор двух `Simulation` через council/отдельный prompt; числа только из фактов |

**Контракт `POST /api/v1/challenge`:**
- Вход = тот же `Scenario`, что у simulate.
- Для каждого из 5 слотов перебрать замену на M1–M14 (+ районы для district-мер); исключить исходный вариант.
- Кандидат → тот же `validate` + `simulate`.
- Выбор: max Score; тай-брейк: выше min district, меньше critical, ниже spent, затем канонический ID/район.
- Ответ: исходный + альтернативный `Simulation`, описание замены, `candidates_checked`, статус `score_improves` | `no_score_improvement` | `no_candidate`.

**Контроль handoff:** для `backend/examples/scenario.json` → замена **M5 Сарыарка → M3 Нура**; Score **56,54307 → 57,20556**; показать потери E2/C1 Сарыарки. Формулировка: сравнение модельных состояний, не «лучший план города».

**Связь с советом:**
1. Challenge считается **только** по кнопке (не тормозит simulate).
2. Агенты/AI получают уже посчитанную пару планов и предлагают компромисс; **не** ищут сценарии сами.
3. Если AI недоступен — показать программный вопрос из полей challenge.

**UrbanLens (в том же этапе, если успеете):** `frontend/src/data/urbanlens.json` + карточки; только проверенные источники (TfL для M1, WHO research для M4/M6). Нет карточки → раздел не показывать. Не влияет на Score.

**Приёмка:** pytest на детерминизм и совпадение с simulate; UI показывает одну замену и цену компромисса.

**Оценка:** challenge 3–4 ч; AI-компромисс 1–2 ч; UrbanLens 2–3 ч (или выкинуть из демо).

## Очередь работ (ближайшие коммиты)

```
A. Result: «Почему изменился Score?» + proof-строка     [дожим этапа 5]
B. Proxy + UI council/stream                            [этап 6]
C. backend challenge + тесты + FE блок                  [этап 7]
D. AI-вопрос по паре планов (fact-bound)                [этап 7]
E. UrbanLens 0–2 карточки или сознательный отказ        [этап 7]
F. README + e2e + тройной demo dry-run                  [этап 8]
G. Только потом 9.1 → 9.2 → …                           [этап 9]
```

**Параллель:** A можно делать на frontend, пока backend пишет C. B зависит от готового stream API (уже есть). D ждёт C.

**Владение (предложение):**
- Backend challenge + тесты — один человек.
- Frontend Result/council/challenge UI — второй.
- README/demo script — совместно в этапе 8.

## Границы (не нарушать)

- Score только из текущего движка / Decimal; UI округляет до 2 знаков **только** для показа.
- Язык: «модельный город», «по правилам синтетической модели»; не «решили проблемы Астаны».
- AI не выдумывает числа и причины загрязнения/мнения жителей.
- Challenge = **одна** замена, не «оптимум города».
- Исследования/UrbanLens не влияют на Score.
